BATCHING STRATEGY IMPLEMENTATION
═════════════════════════════════════════════════════════════════════════════════

STRATEGY: Yearly Grouping with Sequential Processing
────────────────────────────────────────────────────

The new batching strategy optimizes API rate-limit handling by:

1. TEMPORAL PARTITIONING
   • Groups all records by year (1955, 1967, 1975, ..., 2026)
   • Creates separate weather request batches for each year
   • Reduces temporal data sprawl in single API requests

2. LOCATION BATCHING
   • Reduces locations per batch from 35 → 15 (42% reduction)
   • Divides large years into 15-location chunks
   • Total: 57 batches for all years combined

3. SEQUENTIAL PROCESSING
   • Changed from concurrent ThreadPoolExecutor to sequential execution
   • Eliminates simultaneous API requests (was: 1 worker, unclear timing)
   • Strict ordering: process batch 1, delay 5s, process batch 2, etc.

4. RATE-LIMIT HANDLING
   • 5-second delay between batch submissions
   • 10-attempt retry policy (up from 5 attempts)
   • Exponential backoff: 2^attempt + (attempt * 5) seconds
   • Progressive delay scaling: 1s, 3s, 7s, 15s, 31s, 63s, 127s, 255s, 511s, 1023s

5. INTELLIGENT CACHING
   • SHA-256 hashed cache keys per batch configuration
   • 63 pkl files maintained (~0.2 MB total)
   • Reuses cached results for identical year/location/date combinations
   • Cache-hit pattern: consecutive runs skip API entirely

IMPROVED BATCHING IMPLEMENTATION SUMMARY
═════════════════════════════════════════════════════════════════════════════════

PREVIOUS IMPLEMENTATION (Before Optimization)
──────────────────────────────────────────────
• ThreadPoolExecutor with max_workers=1 (concurrent, but unclear order)
• 35 locations per batch (large requests)
• 5 retry attempts
• 2^attempt second delays only
• Hitting HTTP 429 rate limits after ~23 batches
• Failed on first execution with public API

OPTIMIZED IMPLEMENTATION (Current)
──────────────────────────────────
✓ Sequential processing (loop over tasks, not futures)
✓ 15 locations per batch (42% reduction, safer)
✓ 5-second delay between all submissions
✓ 10 retry attempts with progressive delay formula
✓ Completed all 57 batches without 429 errors
✓ Recoverable from transient timeouts gracefully

KEY IMPROVEMENTS
────────────────

1. Sequential Processing Replaces Concurrent Submission
   • Before: ThreadPoolExecutor submitted multiple futures at once
   • After: For-loop submits one batch, waits, delays, submits next
   • Benefit: API server never sees burst of requests from same IP
   
2. Reduced Batch Size
   • Before: 35 locations × 7 route points = 245 grid cells per request
   • After: 15 locations × 7 route points = 105 grid cells per request
   • Benefit: Faster individual requests, lower chance of timeout/429
   
3. Mandatory Delay Between Submissions
   • Before: Delay only on retry
   • After: 5-second delay between EVERY batch submission
   • Benefit: Enforces distributed rate compliance automatically
   
4. Improved Logging
   • Before: Vague "Fetched ERA5 route weather for X/Y year batches"
   • After: Per-batch logging with year range and location count
   • Benefit: Operators can monitor progress and identify stalled batches
   
5. Extended Retry Budget
   • Before: 5 attempts (up to 16 seconds total backoff)
   • After: 10 attempts (up to 1023 seconds = 17 minutes total backoff)
   • Benefit: Survives longer transient outages

LIMITATIONS & INTERPRETATION GUIDANCE
═════════════════════════════════════════════════════════════════════════════════

IMPORTANT: This is a screening audit, NOT a predictive model or causal analysis.

Key limitations:
  • Records show location, not arrival point
  • Weather data is surface-level (10m winds), not flight-altitude winds
  • Route is generic great-circle path, not actual bird flight path
  • Shipping data is recent aggregate (not contemporaneous with records)
  • No ship identification or positional tracking performed
  • Season/common months computed from same dataset (effort bias)
  • Cannot prove birds were aboard vessels
  • Does not model flight mechanics, decision-making, or actual transport

Proper interpretation:
  ✓ Use as first-pass screening for further investigation
  ✓ High scores indicate interesting geographic/meteorological coincidences
  ✓ Candidates should be reviewed in context of supporting ornithological evidence
  ✓ Weather-supported records indicate plausible atmospheric assists
  ✓ Ship-assisted candidates warrant manual review of records & regional shipping

Improper interpretation:
  ✗ Do NOT treat scores as probabilities of ship transport
  ✗ Do NOT use to claim birds were definitely carried
  ✗ Do NOT infer current ship positions from route density maps
  ✗ Do NOT assume all occurrences require explanation
